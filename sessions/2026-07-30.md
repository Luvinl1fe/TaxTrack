## What was completed today

### PR #4 — the repository SQL is under test

Closed the 🟠 gap from milestone 3. The migration runner and every repository
query had only ever been checked by hand on a device, because `expo-sqlite` is a
native module that won't load in Jest.

- `src/db/driver.ts` — a six-method interface `expo-sqlite` already satisfies
  structurally. Tests inject an adapter over in-memory `better-sqlite3` instead.
  Production behaviour is unchanged: the diff to `database.ts` is type-level plus
  one test-only export.
- `test-support/sqliteTestDatabase.ts` — the adapter. Outside `src/` so a Node
  native addon can never be reachable from a Metro bundle; confirmed absent from
  the exported bundle. It translates calling conventions and **nothing else** —
  the statements executed are byte-for-byte the ones that run on the phone.
- 59 tests: migration runner (fresh apply, idempotent re-run, downgrade guard,
  `user_version` holding when a migration throws), category seeding, receipt
  round trips and filters, and the aggregate queries.

The point of it: `totalsByCategory` apportions work-use in SQL while
`deductibleCents()` does the same arithmetic in TypeScript, and nothing proved
they agreed. Now pinned by hand-calculated fixtures, a direct cross-check, a
cross-check against the $300 total, and a sweep over all 101 percentages at eight
amounts. **Mutation-checked:** swapping `ROUND(… / 100.0)` for integer division
fails ten tests. `120000` cents keeps passing under that mutation — it divides
evenly at every percentage, which is why the sweep varies the amount too.

Also had `tsc` reject the first version of the driver interface: `params?` as an
optional argument isn't assignable to `expo-sqlite`'s overloads, which require
the array form. Declared with explicit overloads instead.

### PR #7 — milestone 6, both calculators

Three commits: provisional rates, the vehicle calculator, then WFH logging.

**Provisional rates.** The WFH half was blocked on an unpublished rate, and the
config deliberately holds `null` rather than a stale figure. Rather than stall,
`ATO_RATES[2026]` now carries `provisional: { wfhCentsPerHour: 70 }` — the last
published rate — behind a **structural** safety property, not a convention:

- `getRate()` and `ratesForFy()` still return `null`, so every pre-existing caller
  is untouched, and a test asserts it.
- The only route to the number is `resolveRate()`, returning
  `{ cents, provisional: true }`. **The flag is in the same object as the value**,
  so no caller can obtain the figure without learning it's an assumption.
- A test enforces that a provisional value exists only where the published one is
  `null` — so setting the real rate without deleting the placeholder fails the
  suite rather than shipping both.

This pattern is worth reusing for any rate the ATO hasn't published yet.

**Vehicle calculator** (`src/domain/vehicleCalculator.ts`) — cents per kilometre,
capped at 5,000 km **per car, not per taxpayer**. Two cars at 4,000 km each claim
8,000 km; a test asserts that totalling first, which would cap at 5,000, doesn't
happen. Rounded once at the end, so the same distance logged as one trip or
fifty-eight gives an identical total.

**WFH logging** (`src/domain/wfhCalculator.ts`) — hours per day × the fixed rate.
Per day rather than one annual figure because the ATO now requires a record of the
hours *actually worked*; a four-week sample is no longer accepted.

Three things the ATO's rules forced rather than suggested:

- **Double-claim detection.** The fixed rate already covers electricity, gas,
  phone, internet and stationery — and `phone-internet` and `stationery` are both
  receipt categories here, so the same phone bill can trivially be claimed twice.
  The Home tab finds those receipts, names the amount, and gives the fix both ways.
  It deliberately does *not* flag `tools-equipment`: a desk or computer isn't
  covered by the rate and stays separately claimable.
- **Duplicate-day warning.** Logs *add* to a day rather than replacing it, so
  4 hours entered twice on one date silently doubles the year.
- **`7:30` is rejected, not parsed.** Reading the colon as a decimal is wrong by
  18 minutes a day.

**Separate cards, not one total.** The dashboard's headline card is now
"Receipts", with vehicle and WFH as their own cards. Combining them would invite
claiming fuel or a phone bill on top of a rate that already covers it — which the
ATO forbids. Each card says so.

**The year selector moved into every tab header.** It was on the dashboard only, so
changing the year while reading the receipt list meant knowing to navigate back.

## The ATO's worked example earned its keep

The user pasted the *Cents per kilometre method* page (published 4 May 2026,
QC107246) after it turned out to return **403 to automated fetches** — worth
knowing: ATO pages have to be pasted in by hand, they can't be read directly.

Its worked example — 46 × 27 km + 12 × 106 km = 2,514 km at 88c — is now a test
and reproduces to the cent.

**It also exposed a real discrepancy.** The ATO states **$2,212**, not $2,212.32:
a return is completed in whole dollars, and their example *truncates*. The app
works in cents. Left unchanged deliberately — cents are right for storage and for
totals a user checks against receipts, and only the *return-facing* figure should be
whole dollars. There is no return-facing surface until export, so the boundary is
milestone 7's to pick. Logged 🟠 with the direction settled (truncate, the
taxpayer-safe way) and a test pinning the example either side of the rounding.

No worked example was found for the **fixed rate** method. Worth pinning the same
way when one turns up, especially to see whether it truncates too.

## The bug the device found

**Reported:** a receipt backdated to 2011 didn't appear, and the year couldn't be
changed to go looking for it.

Not intentional. The receipt had saved correctly — `financialYear` derived and
stored right, still in the database. The dev screen simply hardcoded
`const fy = currentFy()`, so no screen could ever display another year. Exactly
what milestone 5's selector fixes. A regression test covers it, including that
May 2011 files under FY **2010–11**, not 2011–12.

Three more surfaced while tracing it, all fixed alongside it:

1. **A year with no ATO rates on file threw and left a permanent spinner.**
   `substantiationStatus` refuses to assume $300 for a year it has no rates for,
   and backdating past 2023–24 makes such a year selectable. Totals now render
   regardless, with a card stating why the test can't be applied — no falling
   back to a remembered threshold, the same rule the config follows for the
   unpublished WFH rate.
2. **Switching to an older year could drop the current year from the picker**,
   leaving no way back. Options are built from `currentFy()` plus the selected
   year, not the selected year alone.
3. **Nothing flagged a mistyped year.** `purchaseDateWarning` warns on a date two
   or more financial years back. Non-blocking — a test asserts the form still
   submits. Two years rather than one because in July people are legitimately
   entering last year's receipts, and warning on the ordinary case teaches them
   to ignore the message.

`FormField` gained a `warning` tier between `hint` and `error`. It renders in the
**error red** at the user's request, so the outline icon is the only thing
distinguishing it from a blocking error — flagged at the time, decided by the
user, and noted on the prop so it isn't "fixed" back later.

**The lesson repeats:** the year-selector bug was in code that typechecked,
linted, bundled and passed 240 tests. The device is still the only real test.

### The same bug appeared twice more

Once the year picker existed, it was built from *receipt* years alone. So a year
holding only trips was unreachable — and later, a year holding only WFH hours.
Both were caught while wiring the next feature, not by a user, but the pattern is
worth naming: **anything that enumerates "years with data" has to consider every
record type, and there are now three.** `financialYearsWithReceipts()`,
`financialYearsWithTrips()` and `financialYearsWithLogs()` are unioned in
`FinancialYearHeaderControl`. A fourth record type in milestone 7 or 8 means a
fourth query, or the bug returns.

published examples.*

**Do this first, before writing any export code:** decide the **whole-dollar
boundary** (🟠 in `KNOWN_GAPS.md`). The ATO's own example proves a return is
