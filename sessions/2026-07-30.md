## What was completed today

### PR #4 — the repository SQL is under test

Closed the 🟠 gap from milestone 3. The migration runner and every repository
query had only ever been checked by hand on a device, because `expo-sqlite` is a
native module that won't load in Jest.

- `src/db/driver.ts` — a six-method interface `expo-sqlite` already satisfies
  structurally. Tests inject an adapter over in-memory `better-sqlite3` instead.
  Production behaviour is unchanged: the diff to `database.ts` is type-level plus
  one test-only export.
- `test-support/sqliteTestDatabase.ts` — the adapter. Outside `src/` so a Node
  native addon can never be reachable from a Metro bundle; confirmed absent from
  the exported bundle. It translates calling conventions and **nothing else** —
  the statements executed are byte-for-byte the ones that run on the phone.
- 59 tests: migration runner (fresh apply, idempotent re-run, downgrade guard,
  `user_version` holding when a migration throws), category seeding, receipt
  round trips and filters, and the aggregate queries.

The point of it: `totalsByCategory` apportions work-use in SQL while
`deductibleCents()` does the same arithmetic in TypeScript, and nothing proved
they agreed. Now pinned by hand-calculated fixtures, a direct cross-check, a
cross-check against the $300 total, and a sweep over all 101 percentages at eight
amounts. **Mutation-checked:** swapping `ROUND(… / 100.0)` for integer division
fails ten tests. `120000` cents keeps passing under that mutation — it divides
evenly at every percentage, which is why the sweep varies the amount too.

Also had `tsc` reject the first version of the driver interface: `params?` as an
optional argument isn't assignable to `expo-sqlite`'s overloads, which require
the array form. Declared with explicit overloads instead.

## The bug the device found

**Reported:** a receipt backdated to 2011 didn't appear, and the year couldn't be
changed to go looking for it.

Not intentional. The receipt had saved correctly — `financialYear` derived and
stored right, still in the database. The dev screen simply hardcoded
`const fy = currentFy()`, so no screen could ever display another year. Exactly
what milestone 5's selector fixes. A regression test covers it, including that
May 2011 files under FY **2010–11**, not 2011–12.

Three more surfaced while tracing it, all fixed alongside it:

1. **A year with no ATO rates on file threw and left a permanent spinner.**
   `substantiationStatus` refuses to assume $300 for a year it has no rates for,
   and backdating past 2023–24 makes such a year selectable. Totals now render
   regardless, with a card stating why the test can't be applied — no falling
   back to a remembered threshold, the same rule the config follows for the
   unpublished WFH rate.
2. **Switching to an older year could drop the current year from the picker**,
   leaving no way back. Options are built from `currentFy()` plus the selected
   year, not the selected year alone.
3. **Nothing flagged a mistyped year.** `purchaseDateWarning` warns on a date two
   or more financial years back. Non-blocking — a test asserts the form still
   submits. Two years rather than one because in July people are legitimately
   entering last year's receipts, and warning on the ordinary case teaches them
   to ignore the message.

`FormField` gained a `warning` tier between `hint` and `error`. It renders in the
**error red** at the user's request, so the outline icon is the only thing
distinguishing it from a blocking error — flagged at the time, decided by the
user, and noted on the prop so it isn't "fixed" back later.

**The lesson repeats:** the year-selector bug was in code that typechecked,
linted, bundled and passed 240 tests. The device is still the only real test.
